# PROMPT — CRÉATION DE L’API D’INTÉGRATION COMPLÈTE DE BIZ-TRANSPAY

Je veux que tu arrêtes de chercher à reproduire simplement une API externe ou à créer une nouvelle logique de paiement indépendante.

**L’objectif est beaucoup plus simple : tu dois prendre les systèmes de transactions qui fonctionnent DÉJÀ dans Biz-transPay et construire par-dessus eux une véritable API développeur permettant à une plateforme externe d’automatiser ces mêmes opérations.**

Tu dois donc **analyser le code actuel de Biz-transPay**, identifier exactement comment fonctionnent actuellement les opérations, puis exposer ces mêmes fonctionnalités à travers une API publique.

---

## 1. RÈGLE PRINCIPALE : NE PAS RECRÉER LES LOGIQUES

Les fonctionnalités actuelles de Biz-transPay fonctionnent déjà.

Tu dois réutiliser **les mêmes services, les mêmes contrôles, les mêmes règles métier et les mêmes mécanismes de traitement**.

Ne crée pas une deuxième logique parallèle.

### Les fonctionnalités à réutiliser sont notamment :

* 💰 Dépôt automatique
* 💸 Retrait automatique
* 🔄 Échange de devises
* 🔗 Paiement par lien
* 📊 Consultation et suivi des transactions
* 💳 Gestion des frais
* 🔐 Vérifications de sécurité
* 🌍 Gestion des pays et opérateurs
* 💰 Gestion des soldes
* ⚡ Traitement automatique des transactions

Si actuellement le dépôt automatique fonctionne déjà correctement, **l’API doit appeler cette même logique**.

Si actuellement le retrait automatique fonctionne déjà correctement, **l’API doit appeler cette même logique**.

Si actuellement l’échange fonctionne déjà correctement, **l’API doit appeler cette même logique**.

L'API ne doit donc pas avoir une version différente du système.

---

# 2. OBJECTIF DE L'API

L'objectif est de permettre à un marchand ou à un développeur d'intégrer **Biz-transPay dans sa propre plateforme**.

Exemple :

```text
Plateforme du marchand
        ↓
API Biz-transPay
        ↓
Système actuel Biz-transPay
        ↓
Opérateur / moyen de paiement
        ↓
Transaction
        ↓
API Biz-transPay
        ↓
Plateforme du marchand
```

Le marchand doit pouvoir automatiser les opérations sans devoir se connecter manuellement à Biz-transPay pour chaque transaction.

---

# 3. DÉPÔT AUTOMATIQUE — PAY-IN

L'API doit permettre à une plateforme externe de demander automatiquement un dépôt.

La plateforme envoie par exemple :

* montant ;
* devise ;
* pays ;
* opérateur ;
* numéro du client ;
* référence de la commande ;
* référence unique du marchand.

L'API doit ensuite utiliser **exactement le même système de dépôt automatique actuellement présent dans Biz-transPay**.

Ne recrée pas un nouveau mécanisme.

### Exemple :

```text
Client achète un produit
        ↓
Plateforme du marchand
        ↓
API Biz-transPay
        ↓
Dépôt automatique actuel
        ↓
Opérateur
        ↓
Paiement
        ↓
Confirmation
        ↓
Biz-transPay
        ↓
Webhook
        ↓
Plateforme du marchand
```

La plateforme doit recevoir le résultat automatiquement.

---

# 4. RETRAIT AUTOMATIQUE — PAY-OUT

Même principe pour les retraits.

Utilise **exactement le système de retrait automatique actuellement disponible dans Biz-transPay**.

Une plateforme externe doit pouvoir envoyer une demande de retrait avec, selon les besoins du système actuel :

* montant ;
* devise ;
* pays ;
* opérateur ;
* numéro du bénéficiaire ;
* référence du marchand ;
* description éventuelle.

Puis Biz-transPay utilise le système de retrait existant.

```text
Plateforme du marchand
        ↓
API Biz-transPay
        ↓
Retrait automatique actuel
        ↓
Opérateur
        ↓
Bénéficiaire
        ↓
Résultat
        ↓
Webhook
        ↓
Plateforme du marchand
```

---

# 5. ÉCHANGE

L'API doit également permettre d'utiliser **le même système d'échange qui existe actuellement dans Biz-transPay**.

Par exemple :

```text
XOF → XAF
XAF → XOF
```

Mais ne limite pas artificiellement les devises : utilise les devises réellement disponibles dans le système actuel.

L'API doit reprendre :

* les taux actuels ;
* les frais actuels ;
* les validations actuelles ;
* les règles actuelles ;
* les limites actuelles ;
* le système actuel de traitement.

**Aucune deuxième logique d'échange ne doit être créée.**

---

# 6. PAIEMENT PAR LIEN

Le système actuel de paiement par lien doit également pouvoir être exploité dans l'API.

Un marchand doit pouvoir créer ou utiliser un paiement par lien depuis sa propre plateforme selon les fonctionnalités déjà disponibles dans Biz-transPay.

L'API doit donc permettre, lorsque prévu par le système actuel :

* création du lien ;
* montant ;
* devise ;
* description ;
* référence ;
* statut ;
* consultation du paiement ;
* confirmation du paiement.

---

# 7. LES 3 IDENTIFIANTS PRINCIPAUX

Je veux que l'intégration soit **très simple**.

Le marchand ne doit pas avoir besoin de 10 clés différentes.

Pour l'intégration API, il doit utiliser uniquement :

### 1. 🔑 Clé publique

```text
PUBLIC KEY
```

Utilisée pour identifier l'intégration Biz-transPay.

---

### 2. 🔐 Clé secrète

```text
SECRET KEY
```

Utilisée côté serveur pour authentifier les requêtes sensibles.

Elle ne doit **jamais être exposée dans le frontend, JavaScript public, application mobile non sécurisée ou dépôt GitHub**.

---

### 3. 🔔 Webhook Secret

```text
WEBHOOK SECRET
```

Cette clé sert à vérifier que les notifications reçues par le serveur du marchand proviennent réellement de Biz-transPay.

---

# 8. CONFIGURATION DU WEBHOOK

Dans le tableau de bord Biz-transPay, le marchand doit avoir une section :

## Configuration API

Il renseigne :

```text
Webhook URL
[ https://monsite.com/api/webhook/biz-transpay ]
```

Lorsqu'il enregistre cette URL, Biz-transPay doit générer automatiquement :

```text
Webhook Secret
**********************
```

Le marchand pourra ensuite copier ce secret dans son système.

### Exemple :

```text
Webhook URL
https://monsite.com/api/webhook/biz-transpay

Webhook Secret
bzt_whsec_xxxxxxxxxxxxx
```

Le secret doit être affiché de manière sécurisée.

Prévoir également la possibilité de :

* régénérer le secret ;
* désactiver le webhook ;
* tester le webhook ;
* consulter les derniers événements ;
* voir les erreurs de livraison.

---

# 9. WEBHOOKS AUTOMATIQUES

Chaque fois qu'une opération importante change de statut, Biz-transPay doit pouvoir notifier automatiquement la plateforme du marchand.

Par exemple :

```text
payment.pending
payment.success
payment.failed

payout.pending
payout.success
payout.failed

exchange.success
exchange.failed
```

Les noms définitifs des événements doivent être déterminés en fonction de l'architecture actuelle.

Le système doit utiliser le **Webhook Secret** pour signer les notifications.

Le serveur du marchand doit pouvoir vérifier la signature.

---

# 10. AUCUN CRÉDIT AVANT CONFIRMATION

C'est extrêmement important.

Pour un dépôt :

```text
Demande créée
      ↓
PENDING
      ↓
Paiement réellement confirmé
      ↓
SUCCESS
      ↓
Crédit
```

L'API ne doit jamais considérer automatiquement une simple demande comme un paiement réussi.

Même chose pour les retraits.

Un retrait demandé n'est pas automatiquement un retrait réussi.

---

# 11. IDEMPOTENCE

Toutes les opérations financières importantes doivent être protégées contre les doublons.

Prévoir une clé :

```text
Idempotency-Key
```

Exemple :

```text
POST /api/v1/payments
Idempotency-Key: ORDER-2026-000125
```

Si le marchand envoie deux fois exactement la même demande à cause d'un problème réseau, Biz-transPay doit reconnaître la demande existante et **ne pas créer deux transactions**.

Cette protection doit utiliser la même logique de sécurité financière que le système interne.


### Paramètres

```json

  "success": true,
  "status": "PENDING",
  "transaction_id": "..."
```

* erreur d'authentification ;
* montant invalide ;
* solde insuffisant ;
* opérateur indisponible ;
* transaction refusée ;
* transaction déjà existante ;
* etc.

**Les exemples doivent être basés sur les véritables endpoints et paramètres de Biz-transPay. Aucun faux endpoint ne doit être présenté comme fonctionnel.**

Le marchand doit pouvoir distinguer clairement :

Pour tester.

Pour les transactions réelles.

Les trois identifiants doivent être différents entre Sandbox et Live.

Exemple :

```text
Sandbox
pk_test_...
sk_test_...
whsec_test_...

Live
pk_live_...
sk_live_...
whsec_live_...
```

Les préfixes exacts peuvent être adaptés à l'architecture finale.

# 19. CE QUE JE VEUX ABSOLUMENT ÉVITER

Ne fais pas ceci :

❌ créer une API fictive ;
❌ créer seulement une page de documentation sans backend réel ;
❌ créer des endpoints qui ne correspondent à aucune fonction réelle ;
❌ créer un nouveau système de dépôt différent du dépôt actuel ;
❌ créer un nouveau système de retrait différent du retrait actuel ;
❌ créer un nouveau système d'échange différent de celui actuel ;
❌ simuler les transactions ;
❌ mettre des données fictives en production ;
❌ demander 10 clés différentes au marchand ;
❌ exposer la Secret Key dans le frontend ;
❌ considérer une transaction PENDING comme SUCCESS.

```text
          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

```

**Le point essentiel est le suivant : l'API Biz-transPay doit être une couche d'intégration au-dessus des systèmes financiers qui fonctionnent déjà dans Biz-transPay. Elle doit permettre à une plateforme externe de déclencher les mêmes dépôts automatiques, les mêmes retraits automatiques, les mêmes échanges et les mêmes paiements par lien, mais de manière programmatique.**

**Avant toute modification, analyse le code existant et identifie précisément les fonctions/services utilisés actuellement pour le dépôt automatique, le retrait automatique, l'échange et le paiement par lien. Réutilise ces fonctions au lieu de les dupliquer. Ensuite, construis les endpoints API autour de ces fonctions et construis la documentation à partir des endpoints réellement implémentés.**
