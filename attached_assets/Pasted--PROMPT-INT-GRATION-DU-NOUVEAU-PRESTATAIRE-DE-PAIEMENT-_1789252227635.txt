# PROMPT — INTÉGRATION DU NOUVEAU PRESTATAIRE DE PAIEMENT DANS BIZ-TRANSPAY

Nous allons maintenant commencer **l’intégration d’un nouveau prestataire de paiement dans Biz-transPay**, mais nous allons procéder **étape par étape** afin d’éviter les erreurs et de garantir une intégration réellement fonctionnelle.

## 1. AJOUTER « PRESTATAIRE DE PAIEMENT » DANS L’ADMIN PANEL

Dans l’**Admin Panel**, au niveau du menu accessible avec les **trois petits points / options**, ajouter une nouvelle rubrique :

> **Prestataire de paiement**

Cette rubrique sera l’espace central permettant à l’administrateur de gérer les intégrations des différentes passerelles de paiement.

### Ne pas modifier les autres rubriques existantes

Les fonctionnalités actuellement présentes dans le menu doivent rester intactes.

Ajouter uniquement :

**Prestataire de paiement**

---

## 2. STRUCTURE DE LA NOUVELLE RUBRIQUE

Lorsque l’administrateur clique sur :

> **Prestataire de paiement**

il doit accéder à une interface permettant de voir et de configurer les passerelles intégrées.

Prévoir une structure professionnelle permettant, pour chaque prestataire :

* Nom du prestataire
* Statut : Activé / Désactivé
* Mode : Test / Production
* Clés API
* Secret API
* Clé publique, si nécessaire
* Webhook URL
* Webhook Secret
* autres paramètres requis par la documentation du prestataire

⚠️ **Ne crée pas de champs arbitraires.**

Les champs exacts seront déterminés **uniquement après analyse de la documentation officielle que je vais fournir.**

> **Webhook Secret à configurer.**

# 5. PREMIÈRE PHASE : UNIQUEMENT LE DÉPÔT / PAY-IN

Pour cette première étape, **nous intégrons uniquement le système de dépôt**, c’est-à-dire le **Pay-in**.

Ne développe pas encore :

* le Pay-out ;
* les retraits ;
* les transferts ;
* les conversions ;
* d'autres fonctionnalités non demandées.

Nous voulons d’abord obtenir **un Pay-in parfaitement fonctionnel**, le tester et le valider.

Ensuite seulement, nous passerons à l’étape suivante.

---

# 6. FLUX DU DÉPÔT

Le fonctionnement devra respecter exactement le flux réel défini par la documentation du prestataire.

De manière générale, le système devra fonctionner ainsi :

```text
Utilisateur
     ↓
Dépôt
     ↓
Choix du pays
     ↓
Choix de l'opérateur / moyen de paiement
     ↓
Montant
     ↓
Création de la requête Pay-in
     ↓
Prestataire de paiement
     ↓
Flux de confirmation requis par le prestataire
     ↓
Paiement confirmé
     ↓
Webhook
     ↓
Vérification de la signature
     ↓
Vérification du statut réel
     ↓
Transaction validée
     ↓
Crédit automatique du wallet
```

Mais **ne suppose pas que ce flux est exactement celui-ci**.

Après lecture de la documentation, adapte le flux aux exigences réelles du prestataire.

---

# 7. RÈGLE DE SÉCURITÉ CRITIQUE

Le wallet de l'utilisateur **ne doit jamais être crédité simplement parce qu'une requête de paiement a été créée**.

La création d'une requête signifie uniquement :

> **Transaction en attente**

Le crédit doit intervenir uniquement après confirmation fiable du paiement.

Exemple :

```text
pending
   ↓
confirmation réelle
   ↓
webhook valide
   ↓
signature vérifiée
   ↓
statut confirmé
   ↓
SUCCESS
   ↓
crédit wallet
```

Si le paiement :

* échoue ;
* est annulé ;
* expire ;
* est refusé ;
* reste en attente ;

le wallet **ne doit pas être crédité**.

---

# 8. PROTECTION CONTRE LES DOUBLONS

Prévoir une protection contre les doubles crédits.

Une même transaction ne doit jamais pouvoir créditer deux fois le compte d'un utilisateur, même si :

* le webhook est reçu plusieurs fois ;
* la requête est répétée ;
* le prestataire renvoie plusieurs notifications ;
* l'utilisateur actualise la page ;
* le serveur reçoit plusieurs appels.

Utiliser un identifiant unique de transaction et un mécanisme d’**idempotence** adapté à la documentation du prestataire.

---

# 9. CONFIGURATION DES FRAIS

L'intégration devra également être compatible avec le système de frais déjà prévu dans Biz-transPay.

Pour le dépôt, conserver la séparation entre :

* **Frais passerelle**
* **Frais plateforme**
* **Total des frais**

Mais ne change pas encore toute la logique de la section Frais sans instruction supplémentaire.

L'intégration doit simplement être conçue de manière à pouvoir utiliser ces paramètres.

---

**Ne crée pas un flux générique qui risque de casser les opérateurs ayant un fonctionnement différent.**
